卷 一

创世

创建型模式 · 从无到有

天地初开，万物未生。这一卷解决的都是同一件事：东西怎么被造出来。核心目标是把 new 收口到一处，让调用方不依赖具体类。

创建型

工厂 Factory

凡人修仙传 · 炼丹房

你把丹方名字往柜台一拍——"来三颗筑基丹"。炼丹师自去配药材、控火候、掐时辰。你只管拿丹，从不需要知道里面放了哪几味药。

炼丹房（工厂）
筑基丹培元丹大还丹
报名字 → 拿丹药，中间过程全部屏蔽
iOSUIButton(type:)、UIFont.preferredFont(forTextStyle:)
心法新增丹药品种，就得改炼丹师手里的方子本（那个 switch）
创建型

抽象工厂 Abstract Factory

凡人修仙传 · 门派制式体系

拜入黄枫谷，领到的是一整套配套的东西：功法《青元剑诀》、制式飞剑、培元丹、道袍。全套同源，用起来不会互相打架——绝不会出现"练着正道功法却拿着魔器"这种自废修为的事。

黄枫谷道统→ 青元剑诀制式飞剑培元丹
魔道道统→ 魔功魔器魔丹
一个道统 = 一整套配套产品，混搭会走火入魔
iOSNSPersistentContainer、主题系统（浅色/深色整套切换）
心法新增"产品种类"要改所有道统，代价最大
创建型

建造者 Builder

凡人修仙传 · 炼制本命法宝

选材 → 塑形 → 刻阵 → 淬火 → 认主。五步一步不能少，顺序错了整件法宝就废了。同一个流程，换个材料就能炼出完全不同的东西——但步骤永远一样。

选材→ 塑形→ 刻阵→ 淬火→ 认主
复杂对象的构建过程被拆成有序步骤，最后一步才交付成品
iOSURLComponents、UIAlertController 的链式配置
心法建造者管"怎么一步步造"，工厂管"造哪一个"
创建型

单例 Singleton

凡人修仙传 · 掌天瓶

天地间仅此一只。不管是谁拿到、在哪个界面用、什么时辰催动，世上就这一只瓶，催出来的灵药也进的是同一处空间。你想用，不用自己造一个，直接去找它就行。

掌天瓶（唯一实例）
韩立 南宫婉 任何想催药的人
拿到的永远是同一只瓶 —— 全局唯一，全局可访问
iOSUIApplication.shared、URLSession.shared、FileManager.default、UserDefaults.standard
心法单例就是全局状态，测试和多线程都要留神；Swift 用 static let shared 天然线程安全
卷 二

铸体

结构型模式 · 塑造形体

有了材料，接下来是怎么把东西组装得更好用。这一卷关心对象之间的组合关系：如何在不改原物的前提下，让它适应新环境、承担新职责、或者被安全地保护起来。

结构型

适配器 Adapter

凡人修仙传 · 灵石兑换阵

天南按"下品灵石"计数，乱星海按"中品灵石"计价。两边标准不同，没法直接交易。中间架一道兑换阵，进来的是天南灵石，出去的是乱星海认的数目——两边都不用改自己的规矩。

天南灵石→ 兑换阵→ 乱星海计价
适配器只翻译接口，不改变任何一方的行为
iOS把第三方 SDK 包成自家协议、AnyView 类型擦除
心法只做接口转换；一旦开始"顺便改逻辑"，它就不是适配器了
结构型

装饰器 Decorator

凡人修仙传 · 给法宝叠加禁制

一柄飞剑本体不变。加一道锐金禁制，更锋利；再叠一道破甲禁制，能破防；再叠一道元磁禁制，能扰敌神识。剑还是那柄剑，但每加一层能力就多一重，而且随时可以拆掉。

① 元磁禁制（最外层）
② 破甲禁制
③ 锐金禁制
飞剑本体
层层包裹，每层和被包对象实现同一接口，所以能无限套娃
iOS给 View 叠圆角+阴影+边框、URLProtocol、Combine 的 operator 链
心法装饰器必须和被装饰对象同接口，否则套不上
结构型

外观 Facade

凡人修仙传 · 万宝楼

买法宝、买丹药、卖材料、打听消息、参加拍卖——全去万宝楼一个地方。楼里有多少鉴定师、多少掌柜在跑腿、货从哪个库房调，你一概不用知道。一个门面，把里头的复杂全挡在外面。

万宝楼（门面）
鉴定拍卖库房账房
对外一个入口，对内一堆子系统
iOSUIImagePickerController、SDWebImage 的高层 API、FileManager
心法外观只是给条捷径，不禁止你直接访问子系统
结构型

代理 Proxy

凡人修仙传 · 傀儡

韩立炼一具傀儡坐镇洞府，自己跑去闭关。外人来拜访，见到的是傀儡——它可以替你挡人、替你传话，也可以直接不让你见到本体。真实对象根本没出场，但事情照样办。

访客→ 傀儡→ 韩立本体
傀儡与本体同接口，访客分不出真假；访问控制、延迟加载都在傀儡这层做
iOS懒加载、NSProxy、URLSession 的远程代理
心法代理和真实对象同接口；代理加逻辑，适配器不加逻辑
结构型

组合 Composite

凡人修仙传 · 阵法套阵

一座护山大阵，由四座子阵拼成；每座子阵，又由若干阵眼拼成。韩立要启动它，只需掐一个诀——大阵自己会递归把底下所有子阵、所有阵眼逐个点燃。对他来说，启动一座大阵和启动一个阵眼，是同一个动作。

护山大阵（容器）
子阵·东 子阵·南 子阵·西
阵眼阵眼 阵眼阵眼
树形结构：单个阵眼与整座大阵被一视同仁，上层不用写 if-else 区分
iOSUIView 层级、CALayer 树、SwiftUI 的 ViewBuilder
心法叶子与容器必须实现同一接口，否则组合的意义就没了
结构型

桥接 Bridge

凡人修仙传 · 法宝形态 × 催动法诀

法宝有形态之分：飞剑、飞刀、宝塔。催动它又有法诀之分：火系、雷系、风系。两个维度各自演化——飞剑配火诀是烈焰剑，宝塔配雷诀是雷塔。不用写"火飞剑/雷飞剑/风飞剑/火宝塔…"这一串，只需 3 + 3 个零件自由拼装。

形态维度→ 飞剑飞刀宝塔
法诀维度→ 火系雷系风系
3 × 3 的组合爆炸，被拆成 3 + 3 的两条独立继承线
iOS协议 + 多个实现自由组合（如 ImageLoader × CachePolicy）、SwiftUI 的 View 与 Style 分离
心法只有"两个维度都会独立变化"时才用；单一维度用继承或策略就够了
卷 三

运术

行为型模式 · 运用神通

形已铸成，接下来是怎么运转。这一卷关心对象之间如何通信、如何分配职责、如何在合适的时机把该做的事交给该做的人。

行为型

责任链 Chain of Responsibility

凡人修仙传 · 拜山门通报

一纸战书递进宗门：山门守卫 → 外门执事 → 执法长老 → 掌门。逐关上递，哪一关接下，后面的关这辈子都收不到。每个关口手里都攥着一根通向上一级的绳子。

山门守卫→ 外门执事→ 执法长老→ 掌门
金色那一关接下，右侧的掌门不再触发
iOSUIResponder 响应链、hitTest 命中测试
心法链必须有尽头，否则事件静默丢失、不报错
行为型

观察者 Observer

凡人修仙传 · 传讯符

宗门大殿贴一张传讯符，所有结丹期长老的神识都挂在上面。钟声一响，全部同时收到消息；至于谁去、谁不去，是他们各自的判断，发消息的人一个都不用管。

传讯符（被观察者）
长老甲长老乙长老丙长老丁
一对多：一个变化，所有订阅者自动收到通知
iOSNotificationCenter、KVO、Combine 的 Publisher、@Published
心法订阅了就要在 deinit 里取消，否则内存泄漏或野指针
行为型

委托 Delegate

凡人修仙传 · 托付与指派

韩立要远赴乱星海，把洞府托付给银月："遇到元婴期修士来犯，传讯给我；其余你自己看着办。"——遇到什么事、由谁决定、决定完怎么回话，事先用一纸约定说清楚。

韩立（委托方）⇄ 银月（被委托方）
一对一：委托方定义"协议"，被委托方实现"具体怎么做"
iOSUITableViewDelegate / DataSource、UITextFieldDelegate
心法delegate 属性必须 weak，否则委托方与被委托方互相持有
行为型

策略 Strategy

凡人修仙传 · 临阵换功法

韩立身上带着大衍决、天雷竹、青竹蜂云剑、元磁神光。对上不同敌人换不同手段——人还是那个人，换的只是这一战用哪门功。而且可以打到一半临时改主意。

韩立（Context）
大衍决天雷竹蜂云剑元磁神光
换功法不用换人：运行时替换，无需重建 Context
iOSJSONDecoder.keyDecodingStrategy、sorted(by:)
心法策略要无状态，别反过来持有 Context
行为型

备忘录 Memento

凡人修仙传 · 留影玉简

韩立每次闭关前，把当前修为、功法状态、体内灵力刻进一枚玉简。万一走火入魔，取出玉简一对照，可以把状态往回拨。玉简本身什么都不会做，它只管"存"。

韩立（原发器）→ 留影玉简（备忘录）
何时回溯由持有者决定← 取回状态
备忘录只负责保存快照，恢复的时机由外部（管理者）决定
iOS状态恢复、UndoManager 撤销栈、Codable 快照
心法快照要不可变；存了不恢复，等于白存
行为型

迭代器 Iterator

凡人修仙传 · 神识扫视

不管面前是散落的灵石、排成阵的阵旗、还是密密麻麻一群妖兽，韩立的神识都只做同一个动作——"下一个"。里面怎么摆、分几层、有几万个，他一概不必知道。

各种聚合→ 统一"下一个"→ 逐个访问
屏蔽内部表示：遍历方式与聚合结构解耦
iOSIteratorProtocol / Sequence、for...in、AnyIterator、enumerated()
心法Swift 里实现 Sequence，就白拿 map/filter/reduce 一整套能力

卷 四

立道

架构模式 · 建立道统

前面三卷讲的是"零件"，这一卷讲的是整座宗门的制度。MVC / MVP / MVVM / TCA 回答的是同一个问题：界面、逻辑、数据这三方，谁跟谁说话、谁有权改状态。它们的演进史，就是一部"把职责越切越清"的历史。

MVC

Model · View · Controller
凡人修仙传 · 掌门 + 弟子 + 藏经阁

掌门（Controller）什么都管：调度弟子、决定今天练什么、还要亲自去藏经阁翻书。弟子（View）负责把宗门的样子展现出来，藏经阁（Model）负责存东西。

问题出在两点。一是掌门太累——所有事都往他身上堆，最后变成一座走不动的巨石（这就是 iOS 圈著名的 Massive View Controller）。二是弟子经常绕过掌门，自己跑去藏经阁翻书（View 直接读 Model），出了事没人知道是谁改的。

它是最朴素的架构，Apple 原生就是这套。小页面用起来飞快，页面一复杂就开始失控。

致命伤：View 与 Model 之间那条虚线。它让"谁改了数据"变得不可追踪，也让 Controller 无限膨胀。

MVP

Model · View · Presenter
凡人修仙传 · 长老 + 传令弟子 + 藏经阁

换了个制度：长老（Presenter）掌握所有推演与决策，传令弟子（View）只干两件事——把长老的指令摆出来给人看，把外面发生的事回报给长老。藏经阁（Model）还是只负责存。

关键改动是：弟子和藏经阁再也不见面了。所有往来必须经过长老。弟子只暴露一个抽象接口（"你能显示什么、能回报什么"），长老不关心对面站的是真人弟子还是一具木偶。

好处立竿见影：想测试长老的决策对不对，随便塞一个假弟子进去就行，不需要真的搭一套界面。这就是它比 MVC 好测的原因。

收益：界面彻底可替换、逻辑彻底可单测。代价：Presenter 自己要手写一大堆"把状态翻译成显示文本"的胶水代码。

MVVM

Model · View · ViewModel
凡人修仙传 · 韩立 + 傀儡 + 情报

韩立（ViewModel）处理一切推演：敌人什么修为、该用什么手段、要不要跑。傀儡（View）只负责照着摆姿势——韩立让它抬手它就抬手，完全不懂为什么。

最妙的一处是：韩立的神识和傀儡是连通的（双向绑定）。韩立心里一变，傀儡立刻跟着动，不需要谁在中间喊一嗓子传话。这就是 MVVM 和 MVP 最大的差别——Presenter 要手动去更新 View，ViewModel 是自动同步的。

所以傀儡可以随便换：换一具新的傀儡（换一套 UI），韩立的推演逻辑一行都不用改。

SwiftUI 天生就是 MVVM：@Published 一改，依赖它的 View 自动重绘。这是目前 iOS 新项目最主流的选择。

TCA

The Composable Architecture
凡人修仙传 · 宗门朝议制度

前面三个制度都有一个共同的隐患：状态可以被到处改。TCA 直接立了一条铁律——只有朝议能改状态，谁都不许私自动手。

State（宗门状态）：灵石多少、弟子几人、领地几何。
Action（折子）：任何人想改，必须写折子递上来，写明"我要做什么"。
Reducer（朝议）：一个纯函数——看当前状态 + 折子，算出新状态。不联网、不写盘，所以极易测试。
Store（议事大殿）：保存着状态和全部流程，是唯一入口。
Effect（外派任务）：朝议上决定"派弟子去探查敌情"，这活儿是异步的，结果回来后，再递一份折子进来。

于是整个宗门变成了一个闭环：状态 → 界面 → 折子 → 朝议 → 新状态。任何时候出问题，只要看折子记录，就知道是谁、在什么时候、改了什么。

适合中大型项目、需要极致可测试性和状态可追溯性的场景。代价是样板代码多、上手曲线陡——小项目上它就是杀鸡用牛刀。

三大模式精讲

上卷是速览，每个模式只有一张卡。下卷把最常用、也最容易写错的三组拆开讲透：责任链、策略、工厂三兄弟。每一讲都配全景图、iOS 真实落点和心法，最后用一场"立即支付"把它们串起来。

责任链 · 拜山门

Chain of Responsibility
一纸战书从山门一路递到太上长老，哪一关接下，后面的关就再也收不到
  • 链就是 next 绳。UIKit 内部把视图 → 控制器 → 窗口 → Application → AppDelegate 串成一条链。
  • 截断 = 不调 super。某个视图重写了 touchesBegan 又不调 super，事件就到此为止——比如你给 View 加了 tap 手势后，控制器收不到这个事件。
  • 链头由点名决定。hitTest 从根视图递归向下，找出"该由哪个视图接这一下"，它成为链头。
  • 经典用法：target 传 nil 的 target-action，会自动沿链找第一个能响应的对象——最纯粹的"谁行谁上"。
  • 心法：链必须有尽头。没人接就等于事件静默丢失，这种 bug 不报错，最难查。

策略 · 临阵换功法

Strategy
修士（Context）不变，变的是丹田里挂着哪门功法（Strategy）
  • 三个角色。抽象策略（协议）、若干具体策略、一个只持有抽象的 Context。
  • 核心收益。同一件事有多种算法，且需要按场景或配置切换时，用它替掉越写越长的 if-else。
  • 判断拆干净没：新增一种算法时，如果需要改 Context 的代码，说明还没拆干净。拆干净后，新增策略只需加一个新类型。
  • 心法：策略要无状态，不要反向持有 Context，否则循环引用跑不掉。

实 战

一场战斗：三个模式同时出场

你在 App 里点了一下「立即支付」，接下来发生的事。

那一指就是一纸战书。hitTest 先当山门守卫，从根视图一层层往下点名，找到"该由哪个视图接这一下"；然后事件沿着响应链往上递，直到某个 ViewController 说「我管」。

ViewController 去炼器阁报个名字，取回一个支付渠道（简单工厂）。渠道内部又持有一条风控校验链——先查限额、再查黑名单、最后查风控等级，哪一环拦下，后面的就不跑了（责任链）。

算手续费时再换一门功法：境内 0.6%、境外 1.2%。人还是那个人，功换一门（策略）。

而整个支付页的颜色、字体、文案，由一套道统统一供给（抽象工厂）——切到"春节皮肤"就是整套换掉，绝不会出现红底配绿字这种走火入魔。

心 法

四条最贵的坑

这四个坑，踩过一次就够。

责 任 链

链必须有尽头

战书一路递到天上都没人接，等于事件静默丢失。这类 bug 不报错，最难查——务必保证每个节点最终要么处理、要么把 next 走到 nil。

策 略

换功法别把人换了

策略应当无状态、单向依赖。策略内部再反向持有 Context，循环引用跑不掉，也说明职责划分出了问题。

抽 象 工 厂

道统不是越多越好

产品族的成员一多，加一个新成员就要改协议 + 所有具体工厂。它对"新增产品族"开放，对"新增产品"封闭性很差。

简 单 工 厂

凡人的智慧也是智慧

那个 switch 确实违反开闭原则，但零心智负担、一眼看懂。产品种类少且稳定时，它就是最优解，别看不起它。
